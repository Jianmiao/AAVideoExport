# AAVE 零 Per-Mod 适配标准（0.3.0）

## 定义

“零 per-Mod 适配”指：AAVE 的生产代码不针对任何具体其他 Mod 做特判；新增一个从未见过的 Mod 时，只要它遵守 AA 的通用运行时契约，AAVE 不需要改代码、也不需要该 Mod 改代码，实际导出仍通过完整同步矩阵。

## 允许的通用机制

- 按 API 族的运行时调用点重写（时钟、媒体、渲染），不按 Mod 身份。
- `RenderControlV1` 或等价通用能力协商。
- 通用 capture scope：导出期间统一接管时间、渲染、音频、启动/菜单边界。
- 通用能力探测：能观测/能接管则支持；不能观测/不能接管则拒绝，并给出原因。
- 通用静态审计：从实际安装集合发现 Mod 名称，不把名称写进产品逻辑。

## 禁止

- 生产代码中的 `if (assemblyName == "X")`、`if (mod.GUID == "...")`、`if (version == "1.2.3")`、`if (mvid == ...)`、`if (type.FullName == "X.Y")`。
- 按 DLL 文件名、启动配置文件名、目录名做 Mod 身份判断。
- `Certified / Observed / Opaque / Rejected` 这类 per-Mod 准入表。
- 为某个 Mod 单独写的 Harmony transpiler/postfix 类。
- 把测试/验收夹具的名称写进生产代码。

## 判定粒度

- **静态门禁**：生产 `src` 字符串字面量中不得出现实际安装 Mod 的程序集名/文件名。违规数必须为 0。
- **动态门禁**：每个完整导出独立跑同步矩阵；不允许用平均、抽样、总帧数相等代替。
- **未知 Mod 门禁**：新增 fixture 后，AAVE 源码和该 Mod 源码都不改；必须实际跑 AA。
- **其他 Mod 不变**：DLL/配置哈希前后一致。

## 能力边界

- 无协议、独占渲染/音频、且无法观测的 opaque Mod 允许被**通用拒绝**；拒绝必须发生在首帧前，不能输出错位电影。
- 拒绝不算“兼容通过”，但符合“不改代码、不特判”的工程边界。
- 任何“拒绝”都必须由通用能力探测产生，不能由 Mod 名称产生。
